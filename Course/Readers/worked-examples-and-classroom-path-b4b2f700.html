Week 5 worked examples and classroom path

Prepared 28 September 2026. This is slide preparation and a teaching route, not an edited PowerPoint. The numerical exercises below are original classroom examples matched to the visualizer. Linked sources supply existing worked solutions, explanations, or documented applications; they are not all shipped-game case studies.

Present in this order

For each stop: pose a concrete question → work the numbers on a slide/board → ask for a prediction → read one small function → change one input in the visualizer. Introduce the symbols before opening a dense graph. Keep the same S=(0,0,0), E=(3,4,0), W=(6,0,0) through the vector sequence.

The core route is displacement, length/unit direction, dot, projection, cross, and matrices. Follow with the arm as a combined application. Interpolation is an extension after students can distinguish positions, directions, and orientations. If time is short, finish the core route rather than compressing quaternion mathematics into unexplained notation.

1. From two positions to displacement

Question: What movement takes us from S to E?

a = E − S = (3−0, 4−0, 0−0) = (3,4,0)
b = W − E = (6−3, 0−4, 0−0) = (3,−4,0)
a + b = (6,0,0) = W − S

Read aloud: “Subtract the starting position from the destination. Each component tells us how far to move on one axis. E connects the two movements; it does not have to be the midpoint.”

Predict: Move only E. Does the total displacement S→W change? No, while S and W stay fixed.

Code: math_core.sub, then add. Explain zip once: it pairs matching components.

Visualizer: Vectors → Two connected vectors → Vectors. Move E, then Restore example.

2. Separate direction from distance

Question: How do we move toward E at a chosen speed?

|a| = √(3² + 4² + 0²) = √25 = 5
u = a / |a| = (0.6,0.8,0)
displacement = u × speed × Δt
             = (0.6,0.8,0) × 2 × 0.5 = (0.6,0.8,0)

Choose consistent distance/time units. The visualizer's coordinates use the Maya scene unit; the speed example is an independent classroom calculation, not a built-in movement simulator.

Read aloud: “The unit vector tells us where to go. Speed and elapsed time tell us how far. If the two points coincide, there is no direction to normalize.”

Code: length, unit, scale. length calls dot(v,v); initially read that as the sum of squared components, then revisit it in the next stop.

Visualizer: Normalize. Double E's distance from S; the blue unit arrow keeps its length. Test Zero vector last.

Documented application: Catlike Coding — Sliding a Sphere develops a controllable character with velocity, input magnitude, and time-based movement. This is a working Unity teaching implementation, not evidence about a named commercial game's controller.

3. Dot product answers an alignment question

First use an easy game-facing question: is a target in front?

forward = (1,0,0), target direction = (0.6,0.8,0)
forward · direction = 1×0.6 + 0×0.8 + 0×0 = 0.6
0.6 > 0: target is in the forward half-space

Then return to the connected vectors:

a · b = 3×3 + 4×(−4) + 0×0 = −7
cos θ = −7 / (5×5) = −0.28
θ ≈ 106.26°

This is the angle between arrow directions. The arm's interior elbow angle is 180°−θ ≈ 73.74°. For a cone with half-angle α, compare unit-vector dot product against cos α. This only tests direction; visibility also needs an occlusion test, and gameplay may require distance and eligibility checks.

Code: dot; then the cosine/angle portion of analyze. Visualizer: Dot / projection; next load Right angle and predict zero before reading the result.

Actual game-code evidence: Valve's public Source SDK, player.cpp. Search for make sure it's in front of the player in the auto-aim code. It subtracts positions, normalizes the target direction, computes a dot product with forward, and rejects negative results. Present this as verified public SDK code, not a claim that every released build uses identical code. The small half-space exercise above is our simplified example.

Material application: Epic — Using Fresnel connects surface normal/view direction to edge-facing material effects. An upward-facing snow mask is another classroom extension: saturate(n·up), then use it as a blend weight. It is not automatically a physical snow simulation or lighting model.

4. Projection builds a vector and a point from a scalar

Question: Where is E's closest point on the infinite line through S and W?

g = W − S = (6,0,0)
u = g / |g| = (1,0,0)
d = a · u = 3
projected displacement = d u = (3,0,0)
H = S + d u = (3,0,0)
residual = E − H = (0,4,0)
residual · u = 0   [check perpendicularity]

Read aloud: “Three is a signed distance. Multiplying by a direction makes a displacement. Adding S makes a point. H is the point, not the purple segment.”

Code: Read the named distance_along_line, projected_offset, and h steps in analyze. Visualizer: Dot / projection; move E and follow H. S=W is undefined. H may lie outside segment SW.

Documented gameplay implementation: Catlike Coding — Physics, ProjectOnContactPlane, removes the normal component to align movement with a ground plane. This is a related plane projection, not the exact line projection shown by our tool:

v_plane = v − (v·n)n, for unit normal n
v=(3,−2,0), n=(0,1,0) → v_plane=(3,0,0)

5. Cross product constructs a perpendicular direction

a×b = (4×0 − 0×(−4), 0×3 − 3×0, 3×(−4) − 4×3)
    = (0,0,−24)
|a×b| = 24 square units
n = (a×b)/|a×b| = (0,0,−1)
n·a = n·b = 0

Predict: Reverse the operands: the result changes sign. Make them parallel: the cross product is zero and no unique unit normal exists.

Code: cross, then unit. Visualizer: Cross / plane. The normal arrow is enlarged 3× for legibility; its displayed numerical value is still a unit vector.

Application: A triangle's two edge vectors construct its surface normal; Epic's Vector Operation Material Expressions documents CrossProduct in the material graph. This establishes an engine operation/application, not a specific shipped game's asset pipeline. In the arm, a bend-plane normal and the elbow pole position are different things.

6. Matrices carry local coordinates into the world

Use Maya's row-vector convention throughout this example. A point has w=1; a direction has w=0.

                ⎡ 1  0  0  0 ⎤
M_translation = ⎢ 0  1  0  0 ⎥
                ⎢ 0  0  1  0 ⎥
                ⎣10 20 30  1 ⎦

[3 4 0 1] M = [13 24 30 1]
x_world = 3×1 + 4×0 + 0×0 + 1×10 = 13
[3 4 0 0] M = [3 4 0 0]       [direction: no translation]

Work one output column before showing the entire multiplication loop. Next show why order matters: scaling x=1 by 2 then translating by 10 gives 12; translating then scaling gives 22.

Code: transform_homogeneous. Visualizer: Spaces & rotations → Local point to world point; rotate the parent. The default live point is the box corner, not the (3,4,0) classroom input; use the runnable companion for the exact numbers above.

Documented engine application: Epic — Skeletal Mesh Sockets shows attachment transforms relative to bones. A weapon/prop grip is the concrete question. Maya parent constraints and Unreal sockets are related transform applications, not interchangeable APIs. Keep World/Local and row/column convention explicit; normals need additional care under nonuniform scaling.

7. Combine the concepts in an arm

Code order: rig.create_arm_chain → rig.create_arm_ik → optionally scene.Demo.set_ik. The first two are short enough to present. The pose-matching function is an instructor extension.

L₁ = L₂ = 5
|L₁−L₂| ≤ target distance ≤ L₁+L₂
0 ≤ r ≤ 10

Visualizer: Arm rig, IK: move wrist then pole; switch FK and rotate shoulder/elbow/wrist. Add the prop last, then compare Point, Orient, and Parent links.

Documented engine example: Epic — Two Bone IK, UE4.27 Content Examples demonstrates a character holding a weapon with IK and hand retargeting. This is an official sample, explicitly an older documentation version. The math explains the constraint; Maya's IK solver performs the actual solve. Do not imply our dot and cross functions implement the whole IK solver.

8. Interpolation as an optional final chapter

Start with a position before a quaternion:

p(t) = (1−t)p₀ + t p₁
p₀=(0,0,0), p₁=(4,0,0), t=0.25 → p=(1,0,0)

Then Euler-component interpolation from (0,0,0) to (90,90,0), t=0.5 → (45,45,0) degrees. Finally show the tool's quaternion endpoints in (x,y,z,w) order:

q₀=(0,0,0,1), q₁=(0.5,0.5,−0.5,0.5)
ω=arccos(q₀·q₁)=60°
q(t)=[sin((1−t)ω)/sin ω]q₀ + [sin(tω)/sin ω]q₁
q(0.5)≈(0.2887,0.2887,−0.2887,0.8660)

Here ω is a quaternion-space angle, half the physical endpoint rotation angle. General SLERP also needs shortest-path sign handling and a near-equal-endpoint case; Maya's API handles the live interpolation. Do not present this fixed-endpoint substitution as a complete general implementation.

Code: scene.Demo.interpolate, then optionally animation.rotation_at and bake_comparison. Visualizer: Spaces & rotations → Orientation interpolation; t=0.5 first, then Play preview for both methods. Position LERP is currently a board/code exercise, not a dedicated viewport mode. Camera/character orientation blending is an application category; the cited quaternion references are explanations, not evidence for a named game's particular interpolation policy.
