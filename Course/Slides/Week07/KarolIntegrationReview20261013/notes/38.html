Handling Expected Warnings in Python Tests — REFINED

Course index · Original notes

When a test deliberately exercises a condition that logs a warning or error, register the expected message with unreal.AutomationLibrary.add_expected_log_error. This tells the automation system which log output belongs to the test scenario.

Register the expectation

The course uses these arguments: a message pattern, the expected occurrence count, and whether matching must be exact. With non-exact matching, the pattern can use a regular expression.

unreal.AutomationLibrary.add_expected_log_error(
    "Failed to set (.*) compression settings to (.*)",
    0,
    False,
)

The example uses 0 for an unrestricted number of matches. The course also observes a failure when an expected message does not appear. Register expectations close to the operation being tested and make the pattern specific enough to avoid accepting unrelated failures.

Understand the demonstrated workaround

The lesson demonstrates emitting a matching warning immediately after registering it, ensuring that a match exists even if the operation does not produce one. This is a workaround for that expectation, not evidence that the operation produced the intended warning.

For a test intended to verify a warning path, exercise the actual condition and check its output. Avoid using a synthetic matching message to conceal that the real path was never reached.

Exact workaround shown in the original

The original's synthetic message is:

unreal.log_warning("Failed to set my_texture compression settings to TC_NORMALMAP")

It is placed after add_expected_log_error(...) to ensure a matching message exists. Keep it labeled as a workaround when comparing with the source. It does not verify that the actual setter produced the expected warning. The source also omits a comma between 0 and False; the corrected registration above includes it.

Original source reproduced below, including transcript wording and intermediate mistakes. Read the refined annotations before reusing code from screenshots.

It's hard to manage Unreal warnings when there are so many parts of code that become deprecated and may be still in use.

These warnings are important but once we are aware of them, they only make reading test reports more difficult.

We cannot suppress them per se but we can "expect" them.

Reference:

_classmethod_ add_expected_log_error(_expected_pattern_string_, _occurrences=1_, _exact_match=False_) → None

Snippet:

unreal.AutomationLibrary.add_expected_log_error("Warning or error to be expected", 0 False)

With occurrences set to 0 this snippet will ignore all occurrences of given error. exact_match is set to False so you don't have to worry about using incomplete warning message.
You can use regular expressions to make this error more generic.

Example:

unreal.AutomationLibrary.add_expected_log_error("Failed to set ((.*)) compression settings to ((.*))", 0 False)

The issue you may run into is that this function does not suppress errors. It expects them.
So if no such error is found then it raises one itself. To prevent that, I log warning as soon as I add expected log error.

unreal.log_warning("Failed to set my_texture compression settings to TC_NORMALMAP")
