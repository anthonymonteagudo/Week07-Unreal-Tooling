Appendix — New to Automated Tests — REFINED

Course index · Original notes

Automated tests provide repeatable evidence that code behaves as intended. Start with a few useful checks and expand them as the tool develops.

Coverage is only one measure

Code coverage reports which code ran during testing. It does not establish that the expectations were useful or that every input and failure case was checked. Even 100% coverage can coexist with weak tests.

Write useful unit tests

A unit test targets a small piece of behavior. Keep it fast, isolated, repeatable, and able to determine its own pass/fail result. Clean up temporary assets or state so one test does not alter another's outcome.

Cover the normal successful case, expected failures, and meaningful boundaries: invalid input, empty collections, unexpected numeric values, failed saves, and exceptions where relevant. Investigate flaky tests that alternate between passing and failing under apparently identical conditions.

Group related checks clearly. In the simple Unreal Python runner used in this course, remember to call the test functions explicitly.

Test the complete workflow too

A functional test checks how the parts work together. For an importer, verify that the asset appears in the correct location with the expected name and compression settings, rather than only testing the helper that creates its filename.

Use your own manual experience with the tool and QA feedback to identify realistic scenarios. If time is limited, prioritize important user workflows and costly failures; a few meaningful tests are more useful than a large collection of trivial checks.

I've shown you how testing works in Unreal and how it is different from typical Python unit testing but you may feel it doesn’t lead you anywhere because you need to gain skill in writing tests before you apply it to UE.

This topic deserves a separate course but you should not be left without any guidance.

Test coverage

Coverage is a percentage of code that is executed in tests.
Keep in mind that coverage does not equal having all possible cases tested.

The higher the value the better but tests quality is more important.
You may have 100% coverage and tests that are useless.

What my tests should be like?

**First, write some Unit tests.
**These are meant to test smallest testable parts of your tools.

Keep those tests Fast and Isolated. If you create/modify some asset, it should be removed/reverted when test finishes. You don’t want your test to break other tests or to corrupt the environment!
Make sure these tests are Repeatable. If tests fails from time to time it can be called flaky”. Limit such tests to minimum.
They should be Self-Validating which means that they have clear output – they either fail or pass.

Make it Thorough:

  • All happy scenarios (everything goes well, no fails)

  • Fail scenarios, especially exceptions! Test what happens if you get incorrect user input, negative values for math operations or maybe cannot save file.

  • Cover all edge cases!

Feel free to keep all those scenarios as separate tests. This way the code will be less cluttered. On the other hand, Epic’s tests often contain many checks in a singe Python function. Thanks to that it takes less space on the screen and there’s lower chance of forgetting to call such function at the bottom of the file.
I advise you to find some middle ground 😊.

**Got the Unit tests? Then write some Functional tests.
**These are meant to test smallest testable parts of your tools.

Unit tests are great but they don’t really test the application. They test some small isolated bits of it. While unit tests may pass, an actual human could completely break your code.

So write tests that act like a human!

That’s it! Got texture importer? Run it from A to Z. Import the texture, check if it was imported to correct location, if the name is right, if compression settings are proper.

Got trouble designing the test? Try to use the tool before you write test for it. Try to break it. If you can, ask you QA team for help.
Then implement scenarios you have figured out.

What now?

Write those tests!

If you are unsure there to begin, pick some simple function or data type and write unit tests for it.

If you are more experienced, think about your priorities. It’s worth having huge unit tests coverage and additional functional tests but gamedev is a dynamic environment. If you are short on time, it may be best to write just few functional tests. They will at least test the tool in a way similar to how it is used.
