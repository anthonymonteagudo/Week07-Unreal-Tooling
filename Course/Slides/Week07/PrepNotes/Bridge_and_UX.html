One prop, two hosts, one clear workflow

Role of this page: detailed design and rehearsal reference. Start with the prioritized preparation plan; choose one follow-up rather than preparing all five alternatives.

Instructor planning draft · 10 October 2026 · Proposed examples, not a changed agenda or an implemented bridge.

Recommendation: open with a Maya → Unreal prop handoff, then use that same prop for an Unreal inspection or setup tool. The material example remains an option; it is not a fixed requirement. A small workflow with visible results will connect the weeks more clearly than a broad tour of APIs.

Opening demonstration · publish, import, revise

Proposed 8–10 minute presentation after rehearsal. Prepare one asymmetric static prop with a recognizable silhouette, a known scale, one material slot, and clean UVs. Use two instances of its mesh in Unreal so a geometry revision visibly demonstrates shared asset data.

  1. Maya: select the prop. A shelf command validates the selection and exports an FBX to a known exchange folder. Show a small report with the object, filename, and destination.
  2. Handoff: briefly show the FBX and a small JSON manifest containing a schema version, source file, asset name, and Unreal destination. JSON carries agreed data; each application's script executes in its own host. No scene-object or Python-object transfer is implied.
  3. Unreal: a prepared command reads the manifest, checks the file and destination, previews the intended import, then imports one static-mesh asset. Place it once, or use a prepared placement step that finds the existing demonstration Actor on repeat runs.
  4. Revision: return to Maya and exaggerate one feature. Export again, reimport into the same Unreal asset, and show both instances updating. Check that scale, orientation, material assignment, and asset identity survive.
  5. One failure: clear the Maya selection or point the import at a missing source. Show a useful message and a clear recovery. End on the working result.

Classroom narration: “The Python language is familiar, but the objects we control belong to different applications. Maya publishes a file and a small description. Unreal reads that agreement and makes an engine asset. When I revise the source, we can update the same asset instead of making a new copy every time.”

Keep the first version as two explicit commands. That makes the boundary visible and avoids spending the opening on networking. The JSON manifest is optional if a fixed FBX path is clearer. A later one-button version can trigger the Unreal command remotely; it should call a known import operation rather than transmit an arbitrary executable script.

Decision to rehearseClassroom-ready behavior
Selection and geometryExactly one intended static prop; explicit handling of transforms, child meshes, units, up axis, and pivot. Use an asymmetric test shape to expose orientation errors.
Import configurationConfirm the importer actually active in UE5.7. AssetImportTask supports import tasks, but Interchange can alter naming/options behavior. Record the tested settings, not just the intended name.
Repeat runsStable destination and asset path; explicit create versus update result. Verify no duplicate asset or Actor, and that saved material assignments remain correct.
RecoveryUse a dedicated demo folder and known source revision. Import/reimport is not guaranteed undoable; demonstrate source restoration/reimport separately from undoable property changes.
FallbackKeep the exported FBX and manifest ready. If Maya is unavailable, begin from those files and explain the already-prepared publish step honestly.

Preparation sources: Autodesk FBX export commands (selection export), Oster Import/Export tutorials, UE5.7 AssetImportTask, and Epic Python best practices (including limits of Undo). Autodesk's Send to Unreal explanation is a useful manual-workflow comparison; FBX export is not itself live synchronization.

UI/UX · a concise teaching approach

UI is how an artist operates the tool; UX includes knowing when to use it, trusting its scope, understanding its outcome, and recovering from problems. A successful script can still be a difficult tool. Begin with a user's job, then choose controls that support that job.

Proposed ten-minute segment: two minutes defining the user/task; three comparing two presentations of the same operation; three showing failure and recovery; two explaining the peer test. This fits the existing proposed UI/UX slot without adding a second implementation lesson.

Question for the makerUnreal-tool example
Who is doing what?“A prop artist needs to update this exported mesh while keeping its destination and assignments.” Start with that task before adding controls.
Can they predict the scope?Display the selected source, target asset path, item count, and create/update plan together. Distinguish Content Browser assets from level Actors.
Can they act confidently?Use a descriptive action such as “Import 1 prop.” Keep the main action obvious; put infrequent settings behind an advanced section. Explain disabled actions.
Can they understand the result?Show changed, skipped, and failed items; offer a way to locate the result. Use text as well as color. Report partial completion honestly.
Can they recover?For a missing FBX, name the file and offer “Choose source.” For property edits, test Undo. For imports, explain the actual restore/reimport route.

A/B demonstration: show a bare “Run” button that silently changes the selection. Then show the same function with a source label, a preview, “Apply to 3 selected Actors,” and a result report. Ask students what they can now predict. Judge the information and behavior, not decoration.

Professional habits: respect host naming and layout conventions; group controls in task order; provide useful defaults; support keyboard focus and readable text; do not encode state in color alone. Test realistic inputs and mistakes, including repeat execution. Keep the workflow independent of whether the front end uses Qt, menus, or an Editor Utility Widget.

Blueprint scope: a prepared Editor Utility Widget is reasonable for presenting a Python tool and discussing its interface. A full Blueprint tool-building lesson would compete with this week's goal. The UI/UX lesson does not require students to learn a second UI framework.

Student worksheet and facilitation

Open the two-page Tool UX Lab Sheet. It contains a task definition, observable success criteria, a first-use test, a recovery test, evidence notes, a design review, and one prioritized change with a retest. Print it using Letter portrait; it can also be used as a discussion guide. No grading or submission rule is implied.

For a proposed 40-minute paired review: 5 minutes to prepare, 12 minutes testing each tool, 7 minutes choosing changes, and 4 minutes for a retest if a quick fix is feasible (otherwise record the retest plan). The tester operates the tool and says what they expect. The author observes and records; record any help rather than disguising it as independent success. Stop if continuing could damage work. A peer session provides useful local evidence, not proof of universal usability.
