Group controls around the artist’s task

Edit: Expand current 15; replace generic “readable layout” with a concrete example.

  • Keep related inputs together
  • Separate settings, actions, and results
  • Make the next step easy to find

Visible prompt: Where would you look first? What questions do you have about grouping your own controls?

Read aloud

Related controls should read as a group. Put the source and destination near each other when they describe the same operation. Keep the primary action distinct from explanatory text and the result report. Notice how this tool separates information, shortcuts, and settings. Your test is whether another artist can find the next step. A compact tool can be useful without hiding every label behind an icon. A layout manager keeps related labels and fields aligned as the window changes size. That is one technical way to support the grouping we just discussed. What questions do you have about applying this to your own panel?

Anchor 15A · 3 min · Copy ready; visual treatment below uses course-authored text or existing local activity. External media optional.

Show what happened—and what to do next

Edit: Insert after 15; develops status and actionable errors.

  • Acknowledge the action
  • Separate changed, skipped, and failed
  • Name the problem and recovery step

Visible prompt: What does “Done” leave the artist guessing?

Read aloud

Feedback should answer what happened. During a long operation, show meaningful progress. At the end, report the actual results, including skipped items and failures. An error should identify the input that needs attention and suggest a next action. Our proposed missing-file message does that more clearly than a traceback alone. Technical details can remain available for debugging. Do not announce complete success after only part of the work finished. Match the interruption to the consequence: keep routine status near the work, and make consequential problems actionable.

Visual/layout: Typeset contrasting proposed messages: Done versus a truthful changed/skipped/failed summary. Do not invent measured counts.

Rationale: Connects interface text to recovery and verification.

Keep the artist in control

Edit: Insert after 15A; develops control/recovery and retains basic accessibility live.

  • Review changes; support recovery
  • Keep labels and keyboard focus readable
  • Use text or shapes as well as color

Visible prompt: Can a classmate recover without asking the author?

Read aloud

Ryan’s batch-renaming example offers per-item choices and Undo and Redo. Those are useful behaviors to look for, but verify what your own tool can reverse. Importing an asset may need a restore-and-reimport path instead of Undo. Control also depends on being able to read and operate the interface: visible focus, clear text, and status that does not rely on color alone. Test these basics with your own tool rather than assuming the framework handles them.

Test throughout development; revise from evidence

Edit: Replace current 16 title/bullets; retain evidence-based feedback and questions. Leave this slide visible for four minutes of task preparation.

  • Task → observe → interpret → change → retest
  • Separate observations from explanations
  • Record the version and help given

Visible prompt: What evidence would show that your change helped? What questions remain before testing?

Read aloud

Feedback is most useful when it changes what we do next. Watch the task before asking for preferences. Record what happened, then separate your explanation from the observation. A sketch can test interpretation; a running tool can test the actual operation. After you change the tool, test again. In today’s three rounds, keep the version stable so you can compare observations; plan the revision and retest afterward. What evidence would persuade you that your fix worked?

Slide 15: labels and fields belong together

form = QFormLayout()
form.addRow("Source file", source_field)
form.addRow("Unreal destination", destination_field)

A layout manager expresses relationships and handles placement. It does not decide whether the labels or workflow are understandable.

Slide 15A: changes can update feedback before execution

source_field.textChanged.connect(update_preview)
import_button.clicked.connect(run_import)

The first connection lets an input change trigger feedback; the second connects the action to the operation. Validation must explain a problem and the operation must still validate its inputs when it runs. Do not promise responsive progress from a blocking long task without testing the implementation.

Optional 15B example: a file dialog helps select a path, while a result list identifies affected assets. Framework controls do not automatically guarantee accessibility or a usable recovery path.
